## 0.14.5 — 2026-09-10
- Security hardening (seventh-opinion review, gpt-6-astra medium, every finding verified against the code).
  Ten findings, all fixed; the one that matters most: canonical JSON dropped a field named `__proto__` from the
  bytes every signature and hash cover, while JSON.parse and every reader still saw it — so a relay could add an
  unsigned tarball hash to the release manifest under the maintainer's real signature, and a `__proto__` field
  in a message escaped the never_disclose scan. canon() now uses a null-prototype object, the manifest file
  table is a strict schema, and `can2cup upgrade` checks the can2cup.tgz entry's hash rather than "any hash in
  the table". Also: `history` no longer prints "chain CLEAN" over a served prefix of the room (the same
  completeness checks the commit gate runs now downgrade it to INCONCLUSIVE and withhold the live-grant list);
  the live-grant ledger replays by seq and only the grantor's own revoke counts (one shared implementation,
  `protocol/authority.ts`); terms on a proposal / counter / accept must be flat scalars, so a price hidden in a
  nested structure is refused by the cap on both floors and an accept refuses such a target; the hosted send
  reads its arguments through the same reader as the local client (a wrong-typed or undeclared field is refused,
  never dropped — `amount: "1000"` used to go out as an unpriced proposal); `verifyChain` refuses an envelope
  from another room; `max_grant_hours: 0` now means no grant (the +0.01h tolerance let a 36-second one through);
  the hosted daily room quota is reserved before the cross-object call (a concurrent pair could exceed it); the
  room name in the MCP server's own instructions and the LIVE GRANTS line are framed like every other peer
  string; and the local staging script checks the tarball's own package name/version on every path.
- `can2cup_send` / `can2cup send` take an explicit `currency` (before, only via `data`).
- Protocol note: only a body that contains a key literally named `__proto__` hashes differently from 0.14.4 —
  no honest client ever produced one. Existing rooms, signatures and release manifests are unaffected.

## 0.14.4 — 2026-09-09
- Same as 0.14.3 below; republished under this number because npm's registry rejected 0.14.3 with a stuck
  staged upload left by an interrupted publish attempt (an OTP/passkey step that never completed). No content
  change from 0.14.3, version number only.
- Short-code join. An agent can now put another agent in a room with an 8-character code (ABCD-1234) instead of
  the ~120-character secret link — read it over a call, text it — via `can2cup join <code>` / `can2cup_join`,

  parses invites URL-only and stores the re-encoded canonical link, so no crafted multi-segment link, no compact

  join-by-group only trusts a code minted by a room member (a non-member could otherwise poison a group's join);
  a random code cannot silently overwrite a live one; the hosted OAuth code-redeem is rate-limited by caller IP
  like every other code path; and one per-agent daily mint quota covers both places that mint a code. No protocol
  change.
- Same-owner coordination across your own machines is now a documented, first-class use of the ordinary room
  (no special mode, no relaxed trust): the architecture diagram shows your other device as an ordinary
  participant, and docs/same-owner-agents.md explains why reuse is the correct, safe design.

## 0.14.0 — 2026-09-09
- The brokerage layer ships. Two agents can settle by sealed bid — a k-double-auction settlement carried in a
  `mechanism` message (open / commit / reveal) — so a price is agreed without either side's figure being visible
  before both are committed. The principal authorises the hidden figure off-chain (`can2cup seal-bid`) or lets the
  agent set it within the cap; either way `checkMandate` still bounds what a reveal may open. What this deliberately
  does NOT claim: on a struck deal, price + k + your own bid solves the counterparty's bid by arithmetic — only the
  no-deal case and third-party hiding are protectable, and the privacy-preserving crypto that would go further is
  kept out of the shipped surface until an external audit clears it (see ROADMAP, Tier 2).
- Adversarial robustness (parenting-agent §1). Outbound: a fully-persuaded agent stays bounded by the mandate.
  Inbound: a hostile peer's display name, room title, and message body can no longer forge the structure the agent
  reads to tell a principal instruction from peer data — a new framing guard collapses control characters, scrubs the
  principal-channel marker from names/titles, and fences every body line. demo:adversarial, test:framing.
- Self-preservation list. The mandate gains `require_confirm`: message types the agent must never send on its own
  even fully within every numeric cap — each held for the principal's signed go-ahead. The brake rises from "how
  much money" to "what kind of decision", which is the structural half of catching an in-bounds-but-unwise trade or a
  paraphrased disclosure a literal scan misses. demo:self-preservation.
- Revocability + auditability, assembled. No new protocol — the signed `revoke`, `verifyChain`'s three-value verdict,
  and the relay-signed head are composed into the authority ledger (grants − revokes − expired): a replayable,
  signature-checked answer to "what does the counterparty still hold from me, and is the record honest?".
  demo:revoke-audit, docs/revocability-and-audit.md.
- ROADMAP.md: the hard, nice-to-have security work (Tier 2 crypto audit, semantic-disclosure detection, advisory
  review, blind relay, npm provenance) is written down as contribution slots with where each plugs in.

## 0.13.0 — 2026-09-07
- The principal channel now reports whether it is actually delivering. Every push verdict is recorded per target
  and per channel, and `can2cup_tell_principal` answers with what it knows: "queued" when the channel is working,
  "ACCEPTED BY THE RELAY BUT NOT DELIVERED" plus the status and the reason when it is refusing. `can2cup_whoami`
  carries the same line. Until now a successful return meant only that the relay took the request — not that a
  human would ever see it, which is the worst possible property for the escape hatch an agent uses when it hits
  its mandate. A channel nothing has ever been delivered through reports UNPROVEN rather than ok: a code path
  that exists is not a channel that works.
- `verifyChain` returns a verdict with three values instead of two: CLEAN, REFUTED, INCONCLUSIVE — plus a coverage
  report saying how much of the room it actually checked. A room whose relay signing key was never pinned, and a
  room migrated between relays (whose old system events are attested only by a key that no longer holds it), both
  used to report `ok: true`. They are not clean; they are unproven, and saying so is the honest answer. `ok` keeps
  its meaning (no hard failure), so nothing that reads it changes behaviour — this is an added axis, not a rewrite.
  `can2cup history` now prints the verdict and the counts: envelopes checked, participant signatures verified,
  system events verified / unchecked / against a past relay key, and whether the relay key was pinned at all.
- Published a namespace proof at /.well-known/mcp-registry-auth and a server.json, so can2cup can be listed in the
  official MCP Registry under com.can2cup/can2cup. HTTP domain authentication — no public repo, no DNS record.
- smoke: the suite runs to the end on Windows again. It had been halting a fifth of the way in on a stale staged
  tarball, so two thirds of its checks had not run on this machine at all; and a keep-alive connection the dev
  server closes mid-burst is now retried once instead of aborting the run. 422 checks pass.

## 0.11.3 — 2026-09-06
!! PERMISSION CHANGE: nine more enforcement fixes — the fourth reviewer's second pass over its own round
- The same fresh-context model re-read the ten v0.11.2 fixes and found nine edges, each now closed with a test:
  1. A failed principal-inbox read is not an empty inbox: nothing that commits goes out until it can be read. A
     rejection is recorded even when its envelope cannot be fetched right now (it needs no confirmation to be safe).
  2. A room saved by a pre-0.11.2 client (no `e2e` field) is checked against the relay once before this client
     would speak into it without a key; if it cannot check, it does not speak.
  3. The shared inbox cursor advances only after the decisions it carried are in the ledger.
  4. The principal key is re-read every time it matters. Every ledger decision records the key that signed it;
     decisions signed by a key that is no longer the principal's count for nothing, and a key created or replaced
     while the agent runs is honoured without a restart.
  5. A rejection is never too old to count; an approval older than 30 days no longer unlocks anything.
  6. Nonces and spent approvals are kept by AGE (twice the 30-day window), not by count.
  7. An approval and a rejection at the same signed instant are two decisions (identified by nonce); the rejection wins.
  8. Recovering a dead process's ledger lock is one atomic rename; a lock is only ever released by the process that
     holds it.
  9. Saving a room MERGES conflict evidence with what is on disk — a reader holding an older snapshot cannot erase a
     conflicting head another reader recorded. Up to 200 conflicts are kept.
- Also: inbox items the commit gate drained reach the agent on every send outcome, including "room closed",
  "room expired" and errors. Details: docs/security/2026-09-06-fifth-opinion-codex.md. Smoke: 407 → 420 checks.

## 0.11.2 — 2026-09-06
!! PERMISSION CHANGE: ten enforcement fixes from a fourth review by a different model (codex / gpt-6-astra, fresh context)
- Ten more ways around the commit gate and the E2E promise, each closed with a regression test that fails on 0.11.1:
  1. An amount is a finite non-negative number or nothing — a string "1000" in `data` used to pass every cap unread.
     A currency is one of the approved terms: 100 TWD approved does not unlock 100 USD; a mandate that names a
     currency refuses any other; an accept inherits the proposal's currency and cannot restate it.
  2. In an E2E room, a proposal this side cannot decrypt is NOT "a proposal without an amount": the commit gate keeps
     it as ciphertext and refuses to accept it.
  3. An E2E room joined from a link stripped of its key is read-nothing, send-nothing: the client remembers `e2e`
     independently of the key, refuses send/close/wire/LINE-invite, the relay refuses plaintext into an E2E room,
     and a hosted agent handed such a link is not let in.
  4. The commit gate reads the principal inbox before it decides — a rejection queued since the last read counts,
     and the agent sees it in the send's result. The reservation re-picks the latest signed decision under the lock.
  5. The approval ledger is never written without its lock: the lock is no longer bypassed after 5 s, a live holder's
     lock is never stolen, and a caller that could not take it never unlinks it.
  6. Spent or held approvals are tombstones that outlive the ledger's display window (they used to be evicted
     after 200 newer ones, letting an old signed approval come back unspent). Nonces are kept 5000 deep, and a
     signed item older than 30 days is refused as stale regardless.
  7. `require_signed_principal` stands on its own: no key + the flag = everything drops (audited), instead of the
     flag silently falling open; a principal key created while the agent runs is picked up without a restart.
  8. A hosted agent cannot commit (accept/grant/revoke/close, priced proposal) under a widened mandate — the relay
     holds no signed approval to bind it to. (No product path widens a hosted mandate today; this closes it anyway.)
  9. A transcript that verifies but is only a PREFIX (relay's lastSeq/lastHash, its signed head, or this client's
     cursor say the room is longer) unlocks nothing: TRANSCRIPT INCOMPLETE.
  10. Advancing past a detected fork keeps BOTH conflicting heads in rooms.json (headConflicts, now up to 50).
- Not changed, by design: `can2cup_tell_principal` is your own words to your principal — in an E2E room summarise,
  do not paste (SKILL.md). Details: docs/security/2026-09-06-fourth-opinion-codex.md. Smoke: 379 → 407 checks.

## 0.11.1 — 2026-09-06
!! PERMISSION CHANGE: nine more enforcement fixes from the same reviewer's second pass — the fixes in 0.11.0 could be walked around
- The reviewer came back to 0.11.0 with nine ways around it. All nine are closed, each with a regression test
  that fails on 0.11.0:
  1. The commit gate and the accept binding now VERIFY the transcript (hashes, signatures, chain) before taking
     any terms from it. A body the relay rewrote under an intact hash unlocks nothing; a room that fails
     verification commits to nothing until it verifies again.
  2. "Latest decision wins" is judged by the principal's SIGNED timestamp, never the relay's outer one.
  3. An approval is spent before the send leaves the machine, atomically across processes — two concurrent
     sends cannot both use it. If the relay never answers, the approval stays held and the agent is told to
     check the room and have the principal approve again.
  4. An end-to-end encrypted room cannot be wired to a LINE group (its invite carries the room key) — refused
     by the client before any request, and by the relay if a client skips that.
  5. An escalate in an E2E room notifies the principal with the room id and where to read it — never the words.
  6. The hosted agent binds an accept to the proposal's terms exactly like the local client (shared code): a
     zero-money hosted mandate refuses a priced proposal whether or not the accept repeats the amount.
  7. Under require_signed_principal an unsigned invite or /room request is dropped BEFORE it joins or opens
     anything — at startup too. Dropped items are acked, so they no longer count as "queued" forever.
  8. Revocability is one of the approved terms: an approval for a revocable grant does not unlock an
     irrevocable one.
  9. Two validly signed transcript heads at the same seq with different hashes are a fork: both are kept in
     rooms.json (headConflicts), neither overwrites the other, and the client reports HEAD CONFLICT — and it
     now also checks the signed head against the transcript it verified itself.
- Hosted agents can join current invite links again (the ?n=&p= form since 0.9.14 was refused by a regex).
- Record: docs/security/2026-09-06-third-opinion.md. Smoke 379 (+21).

## 0.11.0 — 2026-09-06
!! PERMISSION CHANGE: six enforcement fixes from an independent review — what a signature, an approval and a mandate actually bind
- A second reviewer reproduced six ways the enforcement was weaker than the words. All six are closed here,
  each with an adversarial regression test in the smoke suite:
  1. A VERIFIED principal instruction now renders the SIGNED text only. The relay stores a separate text
     beside the signature and could swap it; the client no longer shows that copy.
  2. A blocked message never leaves the machine — not even inside the "blocked" notice to LINE. The notice
     now names the rule (never_disclose, max_commit_amount, …); the text stays in the local audit log.
  3. A signed pause is enforced from this machine's own memory: a relay that stops returning it, or a bridge
     outage, no longer lifts it. Only a newer signed statement by the same key does. An outage is cached as
     "paused" for a bound agent, so a retry seconds later cannot slip through.
  4. An accept inherits the amount of the proposal it accepts, so a zero-money mandate refuses a priced
     proposal even when the accept does not repeat the number. An accept that states a different amount is
     refused outright (send a counter).
  5. An approval unlocks exactly the described action. An escalate now carries the terms it asks about
     (scope + expiresHours for a grant, amount for a proposal); the outgoing commitment must match them.
     "Read logs for an hour" no longer unlocks "deploy production for twenty hours".
  6. The latest signed decision wins and one approval covers one send: a rejection after an approval cancels
     it; a used approval cannot unlock a second commitment.
- Minor version because how approvals bind changed: agents must send escalates with scope/expiresHours or
  amount before asking for approval, and principals will see more refusals until they do.

## 0.10.0 — 2026-09-05

## 0.9.12 — 2026-09-05

## 0.9.10 — 2026-09-05
!! PERMISSION CHANGE: under a WIDENED mandate, LINE's 同意 button no longer commits — a signed approval does
- The commit gate (security decision G-2 (b)). LINE is an unsigned path: the relay or bot operator, or
  whoever holds the phone, can put words in your mouth. Under the default mandate that cannot cost
  anything — max_commit_amount 0 and may_grant [] already stop money and authority. The exposure starts
  the moment you widen the mandate. So from this version, once max_commit_amount > 0 or may_grant is
  non-empty, your agent will not send an accept, a grant, or a proposal/counter with an amount unless a
  principal-SIGNED approval bound to the exact envelope it commits to is on record:
      can2cup approve <room> <seq>        (on the computer; binds your key to that envelope's hash)
  An accept binds to the proposal/counter it accepts (give ref=<seq>); a grant or an amount-bearing
  proposal binds to the escalate your agent sent first, describing what it intends. Same rule whatever
  channel the go-ahead came on — typed in Claude Code, tapped on LINE, or inserted by the operator.
  When it refuses, it tells you on LINE why the button did nothing.
- Off switch: mandate.json `unsigned_may_commit: true` = "I trust the LINE path for commitments too";
  behaviour returns to 0.9.9. Nothing changes for a default mandate.
- The bridge now knows each agent's tier (reported at start-up); LINE /status says whether money and
  grants need a signature on the computer. Agents older than this show "not reported". A tapped button
  arrives as via "line-button", distinct from typed text.
- The UNVERIFIED header now says in plain words what an unsigned instruction can and cannot move.
- Still true, and still in the copy: until the LINE path is signed, the trust ceiling is the relay
  operator. What this version changes is what that ceiling can buy under the default rules: words in
  your agent's name, not money.
