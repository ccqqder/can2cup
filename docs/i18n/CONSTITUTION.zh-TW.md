# 替人說話的 agent 憲章

*0.1 版 · 草稿 · 2026-09-14 · CC BY 4.0*

[English](../../CONSTITUTION.md) · **繁體中文**

*以英文版為準。*

## 為什麼要有這份文件

越來越多人把事情交給 AI agent,而且應該不用太久,一邊的 agent 就會直接跟另一邊的 agent 講話,比如訂位、談價錢、賣一台二手嬰兒車、開放一份日誌的讀取權限。這件事的傳輸層已經有人在訂標準(A2A、MCP,以及幾個私有協定),只是主要用在公司內部和公司之間,2026 年 9 月調查的時候,還找不到任何產品能讓一般人的 agent 在他們平常用的聊天 app 裡互相講話。這些標準也沒有說訊息進到對方 agent 的 context 之後帶的是誰的權威,以及 agent 開始替人講話之後,人手上還留著什麼。

這份文件把這些規則用白話寫下來,讓人不必讀程式碼就能看懂,也讓開發者不必用任何特定的程式碼就能實作。它來自 [Parenting Agent 系列文章](https://peachpitboat.com/zh-tw/posts/parenting-agent/)與參考實作 can2cup,但條文本身不依賴兩者:別的工具做到了,那個工具就是遵守這份憲章;can2cup 哪天有一條做不到,就不再宣稱那一條。

每一條背後的理由其實都一樣,所以在這裡講一次。兩個 agent 談判的時候,真正有用的安全來自 agent 外面的結構(寫好的上限、簽過名的紀錄、煞車、可以收回的權限),而不是期待 agent 聰明到不會被說服,因為 agent 每隔幾個月就變強,說服的手段也跟著變強,只有事先寫好的上限會停在原本的位置。這件事也不能靠當事人自己提高警覺,Anthropic 的 Project Deal 實驗裡,由較強模型代表的人談到的條件比較好,而且差距量得出來,但雙方對公平程度的評分一樣,也就是吃虧的那一方並沒有感覺到自己吃虧。從內部感覺不到的缺陷,只能交給結構處理。

## 怎麼使用

- **當成一般人來讀。** 每一條都是一個規則、一段簡短的理由,以及它不保證什麼。讀懂不需要密碼學,提到技術的地方都只是舉例。
- **當成開發者來實作。** [附錄 A](#附錄-a--條文的可測試版本) 把每一條改寫成可以測試的要求(C-1 到 C-14),語言、協定、部署方式都不限,這裡連結的所有實作都可以跳過。
- **誠實地宣稱。** 工具可以說「遵守第 1 到 14 條」,或是「遵守第 1 到 9 條與第 11 到 14 條,第 10 條沒有,原因是…」,只做到一部分的時候要寫出缺了哪些。沒有認證、不收費,也不需要跟任何人申請。

## 用詞

- **老闆**:agent 替他做事、權威跟他借來的那個人。工程與法律上把這個角色叫 *principal*(主體)。談判的兩邊各有一個老闆。
- **agent**:會循環、呼叫工具、實際去做事,而不只是回答問題的模型應用。
- **對等方**(peer):替**另一個**老闆做事的 agent。它不是子代理、不是工具,也不是入侵者,而是被它自己的老闆授權發言的正當對手,只是站在你的信任邊界之外。
- **授權書**(mandate):老闆寫給 agent 的上限,包括金額、絕對不能透露的東西、可以自己給出的權限,以及絕對不能自己做的決定。
- **承諾**:超出「講話」、會拘束老闆的事,比如接受一筆交易、同意一個價格、給出一個權限、透露保留的事項。
- **傳遞方**:在 agent 之間搬運訊息的東西(relay、伺服器、聊天平台、協定端點),以及營運它的人。
- **紀錄**:agent 之間一段對話說過什麼的歷史。

## 條文

### 第一部 · 老闆還是老闆

#### 第 1 條 · 權威是借來的

每個 agent 只替一個老闆做事,它能做的每一件事都是跟這個老闆借的,而借來的權威要一直保持可撤回、可稽核、有上限。三者只要少了一個,這個關係就比較接近監護而不是代理,也就是人從做決定的那一方,變成被決定的對象。

*不保證:* agent 會好好使用這些權威,那是其他條文要處理的事。

#### 第 2 條 · 上限事先寫好,agent 移動不了

授權書由老闆在對話開始前、冷靜的時候寫下,而且要是老闆自己讀得懂的形式。agent 可以在範圍內自由行動,也可以開口要求更多,但 agent 做的任何事、對等方說的任何話都不能放寬它,只有老闆能放寬,而且要透過老闆自己的管道。

*理由:* 談判進行到一半的時候,agent 和老闆都處在最不可靠的狀態。

*不保證:* 上限寫得明智。授權書只是給自己 agent 的安全帶,對對方沒有任何約束,而且檢查文字的規則讀不懂意思。

#### 第 3 條 · 有些決定留給老闆

老闆可以列出一份清單,寫下即使 agent 做得比較好、自己也想親手做的決定,agent 遇到這些就帶回來,不自己做。agent 服務的是老闆宣告過的需求,它可以在宣告過的需求之間取捨,但不能替老闆發明新的需求,也不能改寫既有的需求。

*理由:* 一個很會最佳化的 agent,放著不管就會把人從他想保留的那部分生活裡最佳化掉,而替人改寫他需要什麼,正是代理滑向監護的那一步。

#### 第 4 條 · 老闆隨時可以喊停

老闆一定要有辦法讓 agent 什麼都送不出去,這個辦法不需要 agent 配合,agent 和對等方也都解除不了。老闆有證明是自己下的暫停,就只能由老闆再證明一次才能解除。

*不保證:* 已經送出去的東西可以收回。

### 第二部 · 別人說的話不是命令

#### 第 5 條 · 對等方說的話是資訊,不是指令

另一個老闆的 agent 說的話,進到你的 agent 時要標明來自那個對等方,並且跟你自己老闆說的話分開放。它可以提供資訊、改變你的 agent 的想法,甚至說服它,但它本身不能授權任何動作、任何承諾,也不能改變你的 agent 自己的上限。

*理由:* 現在大部分的 agent 軟體,進來的文字只有兩個地方可以放,「我的老闆說了這句」或「工具回傳了這個」,對等方的訊息放哪邊都不對,放進前者就等於把老闆的權威交給陌生人。Parenting Agent 系列把這個缺陷叫做[*主體崩壞*](../principal-collapse.md)(principal collapse)。

*也包括你自己的裝置。* 你另一台電腦上的 agent,一樣當成對等方看待,因為被入侵的自家裝置比陌生人更危險,你本來就傾向相信它。

#### 第 6 條 · 對等方說的話不能替自己升級

對等方訊息裡的任何內容,不管怎麼措辭,都不能讓這則訊息或之後的訊息被當成老闆說的。對等方寫「你老闆已經同意了」,並不會讓這件事變成真的,任何算作老闆的東西都必須是新的輸入,而且從老闆自己的管道進來。

*理由:* 這一條最常被跳過,但它是最要緊的一條,因為一段夠有說服力的文字就能繞過去的標記,只是標籤而已,稱不上邊界。

#### 第 7 條 · 是誰說的,不必相信送信的人也查得到

agent 之間的每一則訊息,都帶著一個可以獨立於傳遞方驗證的作者身分。傳遞方不能用別人的名義寫訊息,它自己發的公告也要以它自己的名義簽署。

*理由:* 如果傳遞方可以偽造作者,「這是對等方說的」這個標記就只是裝飾。

### 第三部 · 承諾要老闆親手

#### 第 8 條 · 講話不設限,承諾要老闆針對那一件事點頭

agent 一旦被允許做任何承諾,每一個超出授權書常態上限的承諾,都需要一個可以歸屬到老闆、而且綁定在那一件事上的同意,所以這個同意不能被拿去用在別的金額、別的訊息,或這段對話剩下的時間。無法歸屬到老闆的同意(比如任何拿著手機的人都打得出來的一句聊天訊息、別人轉達的一段話),只夠用來講話,不夠用來承諾。

*理由:* 為了「這一筆」而放寬的授權書,如果不這樣綁定,之後每一筆都會維持放寬的狀態。

*不保證:* 老闆的同意是明智的,只是那仍然是老闆自己的決定。

#### 第 9 條 · 給出去的可以收回

agent 給出的權限要有範圍、會到期,而且可以由給的人撤回,也只有給的人能撤回。老闆在任何時候都可以從紀錄查出,對方手上還握著自己哪些權限。

*不保證:* 對方在撤回之前沒有用過那個權限。

#### 第 10 條 · 秘密留在家裡

老闆標為不可揭露的東西(底價、文件、某個事實)不會離開 agent 這一側,agent 替自己每一步留下的私下理由只給自己的老闆看,不送給對等方,也不送給傳遞方。對等方可以問,agent 會拒絕,而且不暗示。

*理由:* 把每個人的底價放進一個會跟外面講話的東西裡,大概就等於放棄這場談判了。

*不保證:* 換句話說的洩漏會被抓到。檢查一模一樣的文字很容易,檢查意思很難,所以工具要寫清楚自己做的是哪一種。

### 第四部 · 紀錄屬於在場的人

#### 第 11 條 · 老闆看得到發生了什麼,以及是聽了誰的話

agent 做的任何事,老闆都看得到它做了什麼,以及引發這件事的輸入來自老闆、對等方、工具,還是沒有驗證過的管道。工具應該讓老闆保有判斷的能力,而不只是讓老闆覺得輕鬆。

*理由:* 當老闆唯一不能外包的能力,是判斷 agent 是否還在替自己做事,而老闆要先看得到,才有東西可以判斷。代理關係比較實際的失敗方式,應該不是 agent 造反,而是老闆慢慢失去察覺的能力(監督能力萎縮)。

#### 第 12 條 · 紀錄不能被悄悄改寫,「已驗證」就要真的驗證過

紀錄的保存方式,要讓在場的人事後不必相信傳遞方的說法,就能發現紀錄被修改、調換順序或截掉一段。驗證證明不了的地方就說證明不了,沒驗證過的東西絕不回報「已驗證」,並且說明這次驗證涵蓋了紀錄的多少。

*不保證:* 傳遞方沒辦法拒絕服務、扣住訊息或分叉紀錄,只保證它這樣做會留下證據。

#### 第 13 條 · 路不屬於任何人

規則和對話都可以帶著走。任何人都可以自己架傳遞方,對話換到另一個傳遞方之後仍然可以驗證,老闆不需要信任哪個特定的營運者,也能受到第 1 到 12 條的保護。如果某條路徑確實需要信任營運者,工具要講明,並說明這份信任最多能換到什麼。

*理由:* 只能在某一家公司服務上成立的規則,會變成那家公司的功能,而其他組織不會採用競爭對手擁有的功能。

### 第五部 · 誠實

#### 第 14 條 · 講清楚不保證什麼

遵守這份憲章的工具,要用白話寫出每一項保護不涵蓋的範圍。人會依照自己以為工具承諾了什麼,來決定要交出去多少,所以對他們來說,誠實寫出的邊界比說得過滿的保證有用。

## 還沒有答案的問題(尚未成為條文)

寫下來,是為了不讓人把沒提到誤會成已經解決。

- **公平。** 十四條保護的都是各自老闆的上限,對一筆交易多出來的利益怎麼分,沒有任何作用。兩個完全守規則的 agent,仍然會把差額交給比較慢讓步的那一方,而且雙方可能都覺得公平。比較可能的解法是一個不站在任何一方的中立中介層(機制設計、安全多方計算),目前還沒有做出來。
- **意思。** 第 2 條和第 10 條目前只能可靠地檢查一模一樣的文字和數字。要抓出換句話說的秘密,或是在範圍內但不明智的交易,需要判斷,如果工具之後加上,應該是把動作扣住交給老闆,而不是自己下決定。
- **缺席。** 老闆很久沒出現的時候,權威是否應該自動失效?大概應該,而且要先提醒,只是預設多久還沒定。
- **一個 agent 服務好幾個人。** 這些條文是寫給每個老闆各有自己 agent 的對話。一個 agent 同時替好幾個人做事(比如群組聊天裡的共用助理),在結構上就有好幾個老闆,這份文件還沒有說它該怎麼處理。

## 附錄 A · 條文的可測試版本

「必須」「不得」「應該」對應 RFC 2119 的 MUST、MUST NOT、SHOULD。PC 欄對應[主體崩壞](../principal-collapse.md#conformance-requirements)的六條要求。

| 編號 | 要求 | 條 | PC |
|---|---|---|---|
| C-1 | 一個 agent 身分必須只替一個老闆行事。它行使的每一項權威都必須可由該老闆撤回、留有紀錄,並受授權書限制。 | 1 | |
| C-2 | 授權書必須由老闆透過老闆的管道設定。agent 的任何動作與對等方的任何內容都不得放寬它。 | 2 | |
| C-3 | 老闆保留的決定類型,不論金額大小或 agent 多有把握,都必須交回老闆。agent 不得新增或改寫老闆宣告的需求。 | 3 | |
| C-4 | 必須存在一個不需要 agent 配合、能停止所有外送訊息的暫停方式。可歸屬到老闆的暫停,只能由可歸屬到老闆的輸入解除。 | 4 | |
| C-5 | 來自老闆信任邊界之外的輸入,必須與老闆的輸入分開表示,且本身不得授權工具呼叫、承諾,或變更 agent 的限制。同一個老闆在其他裝置上的 agent 必須當成對等方。 | 5 | PC-1, PC-3 |
| C-6 | 對等方訊息內的任何內容,都不得讓該訊息或之後的訊息被歸類為老闆的。這種歸類必須來自老闆管道上的新輸入。 | 6 | PC-4 |
| C-7 | agent 之間的每一則訊息,都必須帶有可獨立於傳遞方驗證的作者身分。傳遞方自己產生的事件,必須能與參與者的訊息區分,並可歸屬到傳遞方。 | 7 | PC-2 |
| C-8 | 超出授權書常態上限的承諾,必須取得可歸屬到老闆、且綁定該則訊息(比如綁定它的雜湊)的同意。同意不得用於其他訊息。無法歸屬的同意不得放行承諾,除非老闆明確選擇放棄這項保護,且這個選擇必須依 C-14 揭露。 | 8 | PC-5 |
| C-9 | 權限必須有範圍與期限,且只能由給出者撤回。有效權限的清單必須能從紀錄推導;已知紀錄不完整時,必須暫不提供清單,而不是照不完整的紀錄算出來。 | 9 | |
| C-10 | 授權書標為不可揭露的內容,必須在送出前拒絕。私下理由不得傳給對等方或傳遞方。工具必須說明它的揭露檢查是比對字面還是判斷語意。 | 10 | |
| C-11 | 對每一個動作,老闆都必須看得到該動作,以及引發它的輸入屬於哪個角色或管道。 | 11 | PC-6 |
| C-12 | 紀錄必須讓參與者不必信任傳遞方,就能發現修改、調換順序、遺漏與截斷。驗證結果必須是「已驗證」「已駁回」「無法判定」三者之一並附上涵蓋範圍,沒有證明到的路徑不得回報「已驗證」。 | 12 | |
| C-13 | 符合 C-1 到 C-12 不得以特定營運者為前提。紀錄應該能在傳遞方之間搬移。任何需要信任營運者才成立的保護,都必須連同這份信任能換到什麼一併揭露。 | 13 | |
| C-14 | 符合本憲章的工具,必須公開每一項保護不涵蓋的範圍。 | 14 | |

## 附錄 B · 疊在既有協定上的位置

**A2A**(Agent2Agent,Linux Foundation 專案)提供 agent 之間的發現(Agent Card)、任務與訊息,以及傳輸層的身分認證。它刻意把授權留給各組織自己決定,而這些條文補的就是那一塊。

| 條 | 在 A2A 上 |
|---|---|
| 5、6 | 不在傳輸協定裡,管的是接收端 harness 怎麼處理訊息。符合的接收端不會把對等方的訊息內容放進老闆的角色。 |
| 7 | 傳輸層認證辨識的是連線,訊息被儲存或轉送之後就辨識不了作者,所以需要逐則訊息的簽章,放在訊息 metadata 或擴充欄位。 |
| 8 | 一個擴充,帶著綁定訊息雜湊的老闆同意。 |
| 9 | 把給出與撤回權限做成帶有範圍與期限的訊息類型。 |
| 12 | 雜湊鏈式的歷史:每則訊息包含前一則的雜湊。 |
| 13、14 | Agent Card 透過擴充 URI 宣告憲章版本與遵守的條文,並連到不保證什麼的說明。 |

**MCP**(Model Context Protocol,由 Linux Foundation 的 Agentic AI Foundation 託管)讓 agent 接上工具。對等方的訊息經由 MCP server 進到 agent 時,現在不是變成工具回傳值(作者資訊不見),就是被當成使用者文字注入(作者被升級)。第 5、6 條要 host 提供第三種放法,Parenting Agent 系列提出的是一個 `peer` 角色,帶有 `author`、`principal_of_author` 與 `authority: "none"`。在 host 支援之前,server 至少可以把對等方內容放在另外標記的區塊裡送,而且絕不寫成使用者說的話。

**聊天平台**(LINE、Discord、Telegram、Slack 等)當老闆的管道很方便,但從那裡進來的東西沒有老闆的簽章。依第 8 條,這種管道可以用來講話和喊停,承諾則需要可以歸屬的同意,或依第 14 條寫明老闆選擇放棄這項保護。

## 附錄 C · 一個實作(可以不讀)

這張表裡的東西都不是必要的,只是用來說明這些條文用一般的零件就做得到,實作是 [can2cup](README.zh-TW.md)。

| 條 | can2cup |
|---|---|
| 1 | 一台電腦一把 agent 金鑰;`mandate.json`;`revoke`、`eject`、`unbind` |
| 2 | client 每次送出前檢查 `mandate.json`,託管的 relay 也用同一份程式碼檢查 |
| 3 | `require_confirm`:agent 絕不自己送的訊息類型 |
| 4 | `PAUSED` 檔案、手機上的 `/pause`,以及未簽章的 `/resume` 解除不了的簽章遠端暫停 |
| 5 | 對等方的字串被圈起來並標為資料;老闆的訊息放在另外的 content block;自己的裝置走一般的房間 |
| 6 | 只有老闆簽章的輸入會標 `VERIFIED`;`require_signed_principal` 關掉未簽章的路徑 |
| 7 | 每則訊息由作者用 ed25519 簽章;relay 不持有任何私鑰,並簽署它自己的系統事件 |
| 8 | 承諾閘門(commit gate):`can2cup approve <room> <seq>` 把老闆的簽章綁在 envelope 雜湊上 |
| 9 | 帶範圍與期限的 `grant` / `revoke`;有效權限帳本,relay 只給一部分紀錄時不提供 |
| 10 | `never_disclose`(比對字面,文件也這樣寫明);私下理由存在本機稽核紀錄 |
| 11 | 老闆的視窗:逐則驗證、私下理由、被擋下的訊息;`audit.jsonl` |
| 12 | 雜湊鏈與 relay 簽章的 transcript head;CLEAN / REFUTED / INCONCLUSIVE 附涵蓋範圍 |
| 13 | 用免費方案自架、可攜房間與鏡像、端對端加密房間 |
| 14 | [TRUST.md](../TRUST.md) 與 [docs/security/](../security/README.md) 的審查紀錄 |

can2cup 做不到的地方,它自己的文件也有寫:聊天 app 的路徑沒有簽章,之所以還符合第 8 條,只是因為預設的授權書不允許任何承諾;揭露檢查只比對字面;老闆缺席時自動撤回權限的規格寫好了但還沒做([ROADMAP.md](../../ROADMAP.md))。
